## Context

变更动机见 `proposal.md`，必须实现的行为见两份能力规范。当前问卷已经由 GitHub Pages 发布，Supabase 生产项目已完成持久化、RLS 与一个私有管理员账号配置，所有产品界面均为英文。本次增量在不改变公开问卷内容和托管架构的前提下增加管理员答卷回收站。

预期负载属于市场调研问卷，而不是高流量事务系统。不过，可靠性仍然要求按身份原子更新、明确的失败状态，以及防止意外重复提交。已接受的身份模型优先考虑便利性而非填写者级别的机密性：只要准确知道姓名和单位，就能够读取并修改对应答卷。

## Goals / Non-Goals

**目标：**

- 生产客户端保持为无需强制构建步骤即可部署的静态文件。
- 使用一份声明式问卷目录统一驱动表单渲染、验证、统计标签、填写者最终检查和 CSV 导出。
- 将问卷状态、持久化、统计、身份验证和 CSV 行为拆分为能够独立测试的浏览器模块。
- 使用数据库约束和函数处理权限敏感操作与并发操作，而不是信任浏览器逻辑。
- 明确呈现未完成、加载中、无数据、冲突、离线、会话过期和服务失败状态。
- 为管理员提供可恢复的答卷移除流程，并确保被移除记录不污染任何统计或导出。

**非目标：**

- 匿名或具有密码学隐私保证的填写者编辑。
- 公开结果、公开管理员注册或填写者账号管理。
- 浏览历史答案版本；仅保留首次创建时间、最新修改时间和当前版本号。
- 邮件发送、通知、文件上传、多语言内容或自建服务器运维。
- 超出数量、比例、搜索、筛选和 CSV 导出的高级统计推断。

## Decisions

### 静态模块化客户端

为 `index.html` 和 `admin.html` 使用语义化 HTML、共享 CSS 和原生 JavaScript 模块。问卷定义、验证、持久化、统计和 CSV 转换分别放在独立模块中。浏览器依赖固定到明确版本；分发源支持时使用完整性元数据。

这种方案不需要生产构建流程，并使 GitHub Pages 部署保持透明。未采用 React/Vite，是因为应用只有两个聚焦界面，不需要框架级状态或路由。未采用 Google Apps Script/Sheets，是因为受保护统计、行级访问、原子 upsert 和并发编辑行为会更难维护。

### 声明式问卷目录

每道题目使用稳定 id、全局编号、章节 id、准确题干、输入类型、选项、必填规则、可选 `Other` 说明和可选条件进行表示。同一份不可变目录同时驱动渲染和报告，避免问卷页面与管理页面之间的题目文字和列顺序发生偏移。

填写者信息页加上 PDF 中的九个章节，共形成十个步骤。问题保留已确认的准确英文题干和选项，同时统一编号为 1 至 34。问题 10 仅在问题 9 包含 `Data` 时激活；问题 6、17 和 26 分别跟随对应的 `Yes` 前置答案。

公开页面固定显示英文帮助文案 `Questions? Contact Dr. Song at hui.song@rmit.edu.au.`，邮箱使用 `mailto:hui.song@rmit.edu.au` 链接。该文案作为页面配置常量管理，不作为问卷答案或数据库字段保存。

### 答卷数据模型

每个标准化身份在 `survey_responses` 中对应一行，概念字段如下：

- 自动生成的答卷 id；
- 用于显示的姓名和单位；
- 标准化姓名和单位；
- 以稳定问题 id 为键的 JSON 对象；
- 整数版本号；
- 首次创建和最后修改时间戳。
- 可为空的删除时间戳和删除操作者用户 id。

对标准化姓名与单位组合施加唯一约束。服务器端在可支持范围内进行兼容 Unicode 的大小写折叠、去除首尾空格并合并连续空格；浏览器端标准化仅用于提示，不作为正确性依据。最新的显示拼写单独保存。`deleted_at` 为空表示当前有效，非空表示位于回收站；`deleted_by` 记录执行软删除的管理员。

JSON 答案适合这份固定的小型问卷，能够避免 34 个紧耦合数据库列。稳定 id 和共享目录确保统计与 CSV 列具有确定性。未采用完全标准化的答案表，是因为目前不需要跨问卷查询，其连接和迁移开销没有必要。

### 受控公开数据库函数

启用行级安全策略，拒绝匿名用户直接查询或修改数据表。仅开放用途受限的数据库函数，用于：

- 载入与所提供标准化身份精确匹配的一份答卷；
- 原子地创建或修改该身份对应的答卷。

保存函数接收预期版本号。新身份创建版本 1；已有有效身份仅在数据库版本匹配时更新，否则返回明确的冲突结果。若同一身份只匹配回收站记录，公开载入返回空结果；该身份重新提交时，保存函数以新答案覆盖旧答案、递增版本并清除 `deleted_at` 与 `deleted_by`。唯一约束负责处理同时发生的首次提交竞争。浏览器会在请求进行时禁用重复提交，但数据正确性不依赖这一界面控制。

Supabase 匿名密钥被视为公开客户端标识。`service-role` 密钥绝不用于 Web 客户端，也不得提交到 GitHub。该边界能够限制批量访问，但无法阻止知道准确姓名和单位的人调用已接受的答卷载入流程。

### 管理员授权

使用 Supabase Auth 的邮箱和密码登录，界面不提供注册。通过 Supabase 管理控制台创建一个管理员，并将其用户 id 加入受保护的管理员允许列表。数据表访问要求用户属于允许列表，而不是只要拥有任意 Supabase 账号即可。

客户端监听身份验证状态变化；退出登录或会话过期时清除内存中的受保护数据并返回登录界面。通用登录错误避免泄露账号是否存在。

### 浏览器端统计

管理员通过授权后，管理页面在浏览器中计算指标和结果分布。这适合预期问卷规模，也能保持公开数据库接口精简。纯统计函数接收答卷数组和问题目录并返回显示模型，以便独立测试。

`Overview` 包含 `Completed Responses`、`Organizations Represented` 和 `Plan to Run Again`。`Choice Questions` 为每道适用题目显示图表，并在每个条形后标注人数和占比。单选题与评分题的分母为该题有效回答数；多选题分母为对该题给出有效回答的填写者人数，因此各选项百分比合计可以超过 100%。

`Open Responses` 提取非空开放答案和 `Other` 补充说明，省略未激活的条件答案，并支持按问题筛选，以及按姓名、单位和回答文字进行不区分大小写的搜索。`Respondents` 提供只读详情。重新渲染前销毁旧图表实例，避免保留 canvas 或重复事件处理器。

所有正常统计视图和 CSV 数据源只载入 `deleted_at is null` 的答卷。回收站记录通过单独的管理员受控函数获取，避免普通统计代码依赖客户端过滤来保证正确性。

### 回收站与删除操作

新增增量迁移 `002_response_recycle_bin.sql`，为现有生产表增加 `deleted_at` 和 `deleted_by`，并创建四个 `security definer` 函数：读取回收站、软删除、恢复和永久删除。每个函数在数据库内部调用管理员身份检查；不给浏览器直接的表级 `UPDATE` 或 `DELETE` 权限。

`Respondents` 每行提供 `Delete`。软删除确认对话框显示姓名和单位，默认焦点为 `Cancel`，成功后重新请求有效答卷与回收站数量。`Deleted Responses` 显示删除时间和删除操作者，并提供 `Restore` 与 `Delete permanently`。永久删除对话框只有在输入文字与填写者完整姓名完全一致时才启用确认按钮。所有对话框使用 modal 行为、支持 Escape，并在关闭后恢复触发按钮焦点。

删除、恢复和永久删除使用独立的管理数据适配器方法。界面只在服务器确认成功后替换内存数据；失败时保留原记录与统计，显示可重试错误，重复点击期间禁用操作按钮。

### 草稿和表单状态

使用一个明确的问卷状态对象。在每次变更后，以身份派生的本地存储键保存未提交草稿；页面重新载入时提供恢复选项；仅在服务器确认保存成功或用户明确丢弃后清除。若 Supabase 已保存答卷比本地草稿更新，则默认使用服务器版本；只有在显示时间戳并获得填写者选择后才恢复较旧草稿。

当前置答案失效时立即清除对应条件答案。章节验证聚焦第一个无效控件，并提供链接到所有错误的摘要。最终检查页面使用与验证逻辑相同的问题目录和条件规则。

### CSV 生成

生成带字节顺序标记的 UTF-8 CSV，以便 Excel 兼容。固定身份字段和时间字段位于前部，随后按问卷目录顺序输出问题列。多选答案采用确定性顺序序列化；`Other` 说明放在相邻的独立列中。字段遵循 CSV 引号规则；以电子表格公式字符（`=`、`+`、`-` 或 `@`）开头的值，在编码前添加单引号。

### 测试策略

纯 JavaScript 模块使用 Node 内置测试运行器，因此测试不要求构建生产网站。测试范围包括与固定预期对比的问卷目录完整性、身份标准化、条件、验证、统计分母、空结果、搜索和 CSV 转义。浏览器级冒烟测试覆盖章节导航、草稿恢复、条件控件、成功提交、冲突显示、管理员身份状态和响应式布局。在应用到生产环境之前，通过一次性 Supabase 兼容 PostgreSQL 环境或专用非生产项目测试数据库迁移。

## Risks / Trade-offs

- [姓名和单位属于弱身份验证] -> 在隐私说明中展示该限制，不公开任何批量读取接口，并保留未来加入填写者身份验证的可能性。
- [公开函数可能遭到自动枚举或垃圾提交] -> 在数据库中验证数据结构和大小、限制函数权限、在浏览器端节流，并在真实流量需要时启用服务商侧滥用防护。
- [免费托管服务存在额度和故障风险] -> 保持客户端轻量、如实显示可重试失败、保留本地草稿、监控 Supabase 用量并记录导出/备份流程。
- [数据量意外增大时浏览器统计可能变慢] -> 按需渲染视图并保持纯计算；只有在实际测量证明必要时，才将汇总移入受保护数据库函数。
- [JSON 答案可能偏离问题目录] -> 保存函数与浏览器同时验证 id、类型、选项值、条件和数据大小。
- [共享设备上的本地草稿可能暴露身份和答案] -> 说明本地草稿行为、提供明显的丢弃操作、按身份隔离草稿，并在成功保存后清除。
- [CDN 依赖可用性可能影响界面] -> 固定明确版本并进行完整性校验；如果 CDN 可靠性不可接受，则记录将依赖文件纳入仓库的备用方案。
- [管理员误删真实答卷] -> 默认使用可恢复软删除；永久删除要求输入完整姓名，且不会提供批量永久删除。
- [恢复时同一身份已被重新提交] -> 重新提交复用原记录而不是创建第二行，因此恢复操作只作用于仍处于回收站状态的记录；若状态已变化则返回冲突而不覆盖。

## Migration Plan

1. 创建 Supabase 开发项目，并应用已审核的数据结构、约束、行级安全策略、管理员允许列表和公开数据库函数。
2. 在 Supabase 中创建唯一管理员账号，并将其用户 id 加入允许列表。
3. 为静态客户端配置 Supabase 项目 URL 和匿名密钥；绝不提供 `service-role` 密钥。
4. 使用合成答卷运行单元测试、浏览器测试、数据库策略测试、并发测试和手工响应式检查。
5. 导出或删除合成记录，然后通过 GitHub Pages 发布静态文件。
6. 在生产环境执行新建答卷、重新载入/修改、冲突处理、管理员登录、图表、开放回答和 CSV 导出的冒烟测试。
7. 对已上线项目应用 `002_response_recycle_bin.sql`，使用合成答卷验证软删除后统计减少、恢复后重新计入、同身份重新提交、永久删除和未授权拒绝，然后删除合成数据并重新发布 GitHub Pages。

回滚方式为禁用或撤销 GitHub Pages 部署，并撤销匿名角色执行公开数据库函数的权限。已有答卷行保持不变，以供管理员导出或受控删除。
